# Use an optional native module for XChat cryptography

Chirp uses an optional Rust Emacs dynamic module built on X's official `chat-xdk` and Juicebox SDK for recovery, private and conversation key ownership, signature verification, message decryption, and outgoing encryption/signing. Reimplementing this security-sensitive stack in Emacs Lisp would duplicate protocol and cryptographic invariants, while a CLI, Node, or browser helper would violate Chirp's no-subprocess transport boundary; keeping the module optional preserves all non-DM Chirp features when it is unavailable. X GraphQL remains in Chirp's `url.el` transport, while only the official native SDK contacts validated HTTPS Juicebox realms.

Recovery is application-session state rather than view state because multiple fresh DM views share one unlocked identity. The requested authenticated X user is checked against the returned registered-key record, carried into recovery, and bound to the recovered native session after the recovered identity key matches that record; outgoing encryption takes no Lisp sender override. Each explicit PIN submission creates one native job and one high-level SDK recovery call; Chirp never retries it automatically but permits a later, separately confirmed submission. Workers own only Rust values and communicate through polling keyed by both an application epoch and a native job ID, never by retaining an `emacs_env`, Lisp value, or callback. Cancellation drops the in-flight Tokio future, explicit application shutdown cancels and joins owned work before destroying all native SDK state, and GC finalization only requests cancellation and detaches so it cannot block Emacs. PINs and key material stay native; Lisp receives only non-sensitive status, signature-verified domain data, and opaque encrypted/signed envelopes for one fixed X write.
